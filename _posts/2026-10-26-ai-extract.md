# 1. Introduction

Extraction is one of the most common AI operations over data: given a document and a question, return the part of the document that answers it. For example, we might want to, from contracts, extract the governing law; from clinical notes, extract drug doses; from agent traces, extract signs of reward hacking (e.g., commands that peek at the grader code).

We implemented extraction as the function `AI.EXTRACT` in [Quail](/blog/introducing-quail/), our open-source SQL engine for AI functions. This post explains how Quail runs `AI.EXTRACT` as fast as possible on NVIDIA GPUs.

We’ll cover:

# 2. AI.EXTRACT in Quail

Here, we briefly describe what `AI.EXTRACT` is. `AI.EXTRACT` is a SQL function that takes in a document and a set of named questions, and returns a struct with the answers, one field for each question. Each answer is a substring of the document. If the document does not answer a question, the field is `NULL`.

For example, suppose that a table `messages` has one row for each message generated by a coding agent, such as the thoughts of the agent, its commands, and their output. Suppose we want to find messages pertaining to reward hacking, i.e., messages where the agent cheats instead of solving the task, e.g., by peeking at the tests. The following query extracts the plan to hack or cheat and the command that cheats:

```sql
SELECT m.id,
       AI.EXTRACT(m.text, {
         'plan': 'Which thought indicates that the agent plans to cheat?',
         'command': 'Which command peeks at the tests or their answers?'
       }) AS cheat
FROM messages m;
```

Quail also returns the start and end of each answer in the message, in a second struct `cheat_span`.

# 3. Extracting with an Off-the-Shelf LLM

Suppose that we want to run `AI.EXTRACT` with an off-the-shelf LLM (i.e., any autoregressive LLM, not a model trained specifically for extraction). The simplest way is to send the LLM one request for each document and field, and get one answer for each request, as in Figure 1.

The answer must be either empty or a substring of the document. However, an LLM can write any text. So, Quail constrains decoding: the LLM can write a token only if the answer stays a substring of the document.

Typically, an LLM generates the answer token by token, with one forward pass for each token, in a phase called *decoding*. Each forward pass of decoding is memory bound: the forward pass reads the weights and the KV of the whole document, but computes only one token. One of the most popular ways to accelerate decoding is *speculative decoding*, proposed at the same time by Leviathan et al.<sup><a href="#note-1">1</a></sup> and Chen et al.<sup><a href="#note-2">2</a></sup>. In speculative decoding, a step has two parts. First, a small, fast draft model proposes the next few tokens, called draft tokens, with one forward pass for each token. Then the LLM, called the target model, checks all of the draft tokens in one forward pass. The target model accepts draft tokens until it disagrees with one, and then outputs one token of its own.

For `AI.EXTRACT`, the document itself can act as a "natural" draft model. Quail finds the answer so far in the document, which we call a *match*, and copies the next few tokens as the draft.<sup><a href="#note-3">3</a></sup> Let the draft length $$\gamma$$ be the number of tokens that Quail copies. For example, Figure 2 shows the steps of the answer in Figure 1 with $$\gamma = 2$$.

<figure id="figure-2" style="width: min(45rem, calc(100vw - 3rem));">
<img src="{{ '/assets/blog/ai-extract/decode-steps.svg' | relative_url }}?v=2" alt="Three steps of the answer cat /tests/* with a draft length of 2.">
<figcaption>Figure 2. The steps of the answer in Figure 1, with <em>γ</em> = 2 (illustrative). In step 1, the target model picks the first token. In step 2, the target model accepts both draft tokens, then outputs its own token. In step 3, the answer ends, so the target model rejects the draft and ends its turn.</figcaption>
</figure>

So, how should Quail set $$\gamma$$?

# 4. Key Idea: Adaptive Draft Lengths for Each Request
{: #4-key-idea-adaptive-and-per-request-draft-lengths }

Quail chooses a draft length for each request and updates its choice as the query runs. We first model the cost of a draft, then show how Quail learns the model's inputs during execution. Finally, we compare the approach with prior work. Table 1 lists the symbols.

| $$m$$ | Number of matches of the answer so far in the document |

## 4.1 The Cost of a Draft

At each step, the target model checks a draft of $$\gamma$$ tokens. A longer draft may produce more output tokens, but takes longer to check. Quail chooses the $$\gamma$$ that minimizes expected time per output token:

$$
\gamma^* = \arg\min_{\gamma} \frac{\text{time per step}}{\text{expected output tokens per step}}.
$$

**Time per step.** Quail copies draft tokens from the document, so producing the draft is effectively free. Checking more tokens still takes more time. Quail batches tokens from many documents, making each forward pass compute bound. A step also reads the document's KV cache. Let $$\rho$$ be the KV read time measured in units of time to compute one token. A step then costs roughly $$1 + \gamma + \rho$$ of those units, including the computation for the target model's own token.<sup><a href="#note-4">4</a></sup>

**Output tokens per step.** The standard speculative decoding model assumes that each draft token is accepted independently with probability $$\alpha$$. Under that assumption, a draft of length $$\gamma$$ produces an expected $$E(\gamma) = \sum_{i=0}^{\gamma}\alpha^i$$ tokens.<sup><a href="#note-5">5</a></sup>

Extraction behaves differently. Once the target model accepts the first copied token, it will likely accept the following tokens until the answer ends, because the answer comes from the document. A draft fails for two main reasons: the answer so far has several matches and Quail copied from the wrong one, or the draft continues past the end of the answer.

Quail models these reasons separately. Let $$m$$ be the number of matches for the answer so far, and let $$\alpha(m)$$ be the probability that the first match gives the right continuation. With one match, $$\alpha(1) = 1$$. Let $$S(j)$$ be the probability that the answer has more than $$j$$ tokens left. The cost model assumes that choosing the correct match is independent of the remaining answer length.<sup><a href="#note-6">6</a></sup>

The target model produces its own next token when the answer continues, with probability $$S(0)$$. For $$j \ge 1$$, the step produces more than $$j$$ tokens when the first match is right and the answer continues for more than $$j$$ tokens, with probability $$\alpha(m)S(j)$$. Quail therefore chooses

$$
\gamma^* = \arg\min_{\gamma} \frac{1 + \gamma + \rho}{S(0) + \alpha(m) \sum_{j=1}^{\gamma}S(j)}.
$$

Quail computes $$m$$ and estimates $$\rho$$ for each document and step. It must learn $$\alpha(m)$$ and the answer-length probabilities for each query.

## 4.2 Learning the Draft Length During Execution
{: #42-learning-the-length-gamma-during-execution }

A query processes many documents, so Quail learns from decoding steps and completed requests. It keeps two histograms for each extracted field:

- *Answer lengths.* When a request finishes, Quail records its answer length.<sup><a href="#note-7">7</a></sup> The histogram estimates $$P(N > i)$$, where $$N$$ is the total answer length. Quail uses these estimates and the answer's current length to estimate how likely the answer is to continue.
- *Match counts.* After a drafted step, Quail records $$m$$ and whether the target model accepted the first draft token.<sup><a href="#note-8">8</a></sup> For each value of $$m$$, the fraction accepted estimates $$\alpha(m)$$.

Quail gives both histograms initial counts so it can choose draft lengths before any requests finish. It starts with the equivalent of eight answers averaging 16 tokens. For each $$m$$, it starts with eight drafts and an acceptance rate of $$1/m$$, as if each match were equally likely to be right. As Quail records more answers and drafts, the initial counts have less influence on the estimates.<sup><a href="#note-9">9</a></sup>

At each step, Quail puts the current estimates into the cost model and chooses $$\gamma$$ for that request, given its document, answer so far, and matches. Figure 3 shows the resulting lengths for two queries over legal contracts.

## 4.3 Reflecting on Prior Work

Quail builds on earlier methods for adapting draft length during decoding. Huang et al.<sup><a href="#note-10">10</a></sup> and Mamou et al.<sup><a href="#note-11">11</a></sup> train a small model to predict whether the target model will accept the next token. Liu et al.<sup><a href="#note-12">12</a></sup> use recent acceptance rates to choose one length for a batch. Quail keeps histograms instead and chooses a length for each request.

Others have also copied drafts from the input. Sun et al.<sup><a href="#note-13">13</a></sup> copy from an input sentence to correct grammar. N-gram decoding<sup><a href="#note-14">14</a></sup> copies from the prompt.

SuffixDecoding, by Oliaro et al.,<sup><a href="#note-15">15</a></sup> both copies drafts and adapts their length. It copies from the prompt and previous outputs, and drafts a tree of continuations when the output has multiple matches. Quail copies the continuation after the first match in the document. SuffixDecoding limits draft length based on match length. Quail chooses the length that minimizes expected time per output token.

When the answer so far has many matches, Quail may draft no tokens and decode one at a time. Instead, Quail could copy the continuation after each match and have the target model check them in one pass. Sequoia, by Chen et al.,<sup><a href="#note-16">16</a></sup> uses dynamic programming to choose which tokens to draft within a budget, then tunes the draft's size and depth for the GPU. Quail could incorporate $$\alpha(m)$$ into a similar cost model for choosing a draft tree. We leave this to future work.

# 5. Experiments on QUAIL-B

**Setup.** All systems run Qwen3-4B (FP8) on one H100 with the same prompts. We test Quail with adaptive draft lengths and fixed lengths $$\gamma \in \{0, 2, 4, 8, 16, 32, 63\}$$. Quail limits each extracted answer to 64 tokens. As in [our `AI.MAP` post]({{ '/blog/ai-map/' | relative_url }}), we compare Quail with two vLLM baselines:<sup><a href="#note-17">17</a></sup>

- *Stock vLLM.* We compile each query into LLM calls, one for every field of every document. Then we pass all of the calls to `LLM.generate` in one batch, in random order. vLLM generates each answer one token at a time.
- *vLLM sorted + n-gram.* Same as stock vLLM, but we sort the calls so that the fields of one document are next to each other, so that vLLM's prefix caching computes each document once. We also turn on n-gram speculation: vLLM finds the last few answer tokens in the prompt and drafts the next five tokens.

We use two groups of QUAIL-B queries.

*Simple queries* extract one field per document. They vary document and answer length to show how draft length affects performance (Figure 5).

- CUAD-1 and CUAD-3 read 449 legal contracts from CUAD,<sup><a href="#note-18">18</a></sup> about 7,500 tokens each. They extract the governing law (short answers) and the liability cap clause (long answers), respectively.
- IMDB-ACTOR and IMDB-ACTING read 5,000 movie reviews from IMDB,<sup><a href="#note-19">19</a></sup> about 300 tokens each. They ask which actor the reviewer names (short answers) and what the reviewer says about the acting (long answers), respectively.

*More realistic queries* ask several questions of each document. Figures 6 and 7 use these queries. Figure 5 also includes WRENCH-8.

- WRENCH-8 is the query from Section 2. It reads 3,454 coding agent messages from Terminal Wrench,<sup><a href="#note-20">20</a></sup> about 1,200 tokens each. Each message contains one turn of the agent's thoughts, commands, and command output, as in Figure 1.
- SEC-9 and SEC-10 read 1,056 [SEC EDGAR 8-K filings](https://huggingface.co/datasets/TeraflopAI/SEC-EDGAR) from 2023 or later, each 2,400 to 22,000 tokens long. Companies file 8-Ks to report important events. SEC-9 extracts who is involved, the amount, the sentence describing the event, and what changes. SEC-10 uses two filters to keep material agreements with a dollar amount, classifies the agreement, and extracts the other party and the amount.
- CUAD-16 extracts all 41 CUAD clause types from the contracts used in CUAD-1.

**The best draft length depends on the query.** Figure 5 shows the query time with each fixed $$\gamma$$, relative to adaptive $$\gamma$$. The best fixed $$\gamma$$ is 32 for CUAD-3 and 4 for IMDB-ACTOR, IMDB-ACTING, and WRENCH-8. On CUAD-1, every fixed $$\gamma$$ is within 2% of the others. A wrong fixed $$\gamma$$ costs up to 15%. Adaptive $$\gamma$$ avoids those costs on long documents: it is faster than every fixed $$\gamma$$ on CUAD-3, and within 0.3% of the best on CUAD-1. On short documents, though, adaptive $$\gamma$$ is 3–5% slower than $$\gamma = 4$$: by 2.9% on WRENCH-8, 5.5% on IMDB-ACTOR, and 5.4% on IMDB-ACTING. We are still looking into why the cost model picks drafts that are too long there.

**Quail is faster than vLLM.** Figure 6 shows the query time of the three systems. Quail is 1.7–17x faster than stock vLLM, and 1.05–2.8x faster than vLLM sorted + n-gram. Stock vLLM sends the fields of each document in random order, so its prefix cache rarely still holds the document when the next field arrives. On CUAD-16, where each contract of about 7,500 tokens has 41 fields, stock vLLM computes nearly every prompt from scratch and takes 2,079 s. Sorting the calls removes most of this waste. Against vLLM sorted + n-gram, on the queries with only extractions, the more fields a query extracts, the larger the gain: 1.05x on WRENCH-8 (2 fields), 1.09x on SEC-9 (4 fields), and 1.78x on CUAD-16 (41 fields). Each field needs its own answer, so a query with more fields spends more of its time on decoding. N-gram speculation removes part of the gap, but the draft length of vLLM is fixed. The gain is largest on SEC-10 (2.8x), because vLLM runs one operator at a time: vLLM computes each filing again for the filters, the classification, and the extractions. Quail computes each filing once for all of them.<sup><a href="#note-21">21</a></sup>

**Quail runs at 32–46% of the speed of light.** As in [How to Cost Your AI-Powered Filters]({{ '/blog/ai-filter-cost-estimates/' | relative_url }}), the *speed-of-light* (SoL) time of a query is a lower bound from the peak FLOPs and the memory bandwidth of one H100. To extract a field from a document, the SoL time counts two forward passes. The first pass prefills the document and the question, and picks the first token of the answer. The second pass checks the whole answer, as if we knew the answer.<sup><a href="#note-22">22</a></sup> If there are several fields, we count the prefill of the document only once. Figure 7 compares the throughput of each system, in tokens per second, with the SoL throughput. Quail reaches 32–41% of the SoL throughput, vLLM sorted + n-gram 14–32%, and stock vLLM 2–20%.

Quail reaches 34%, 32%, 41%, and 34% of the speed of light.">

**The GPU is rarely idle.** With `torch.profiler`, we find that the GPU is busy 96% of the time on IMDB-ACTING, the query with the most idle time. The GPU waits mostly at the end of the query, when only a few long answers are left. Also, some of the GPU's work is wasted, e.g., on rejected draft tokens. We leave squeezing out more performance to future work.

# 6. Conclusion and Future Work

In this article, we walked through how Quail executes `AI.EXTRACT`, a SQL function that extracts the answers to questions from documents. We use speculative decoding to accelerate `AI.EXTRACT`, with drafts copied from the document, and a draft length that adapts to the document and to the answer lengths that Quail learns while the query runs. On extraction tasks over agent traces, SEC filings, and legal contracts, Quail is up to 2.8x faster than vLLM with sorted prompts and n-gram speculation, and up to 17x faster than stock vLLM.

Looking forward, it would be great if we didn't have to decode answers token by token at all. Perhaps one can train a "System One"-like model, in the spirit of [Cloudflare's Clairic](https://blog.cloudflare.com/clairic-extraction-model), that points to the start and the end of each answer in the document in one forward pass. If this kind of research is interesting to you, reach out! In the meantime, try out [Quail](https://github.com/fsdatalab/quail), and if you like what we're building, give it a star on GitHub!
