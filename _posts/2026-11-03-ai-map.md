Our implementation of <code>AI.MAP</code> in Quail achieves <strong>2.1–6.2x higher throughput</strong> than stock vLLM on the same model and GPU. # 1. Introduction

People often want to generate text in bulk: for example, summarize every contract in a dataset, or describe what an agent did in each of thousands of agent traces. In inference-speak, this is *bulk decoding*: an LLM generates text for every row of a dataset, which can have tens of thousands of rows. In Quail, our inference engine for SQL queries with AI functions, users express these workloads with the `AI.MAP` function.

Bulk decoding can be slow, since generating each output token requires a forward pass through the model. But unlike chat, where latency matters for _each_ request, we only care about finishing the entire query (a group of requests) as quickly as possible. This lets us trade off latency on individual rows for higher throughput across the dataset.

In this post, we'll explain how `AI.MAP` works, how Quail optimizes bulk decoding, and why these optimizations achieve up to 6.2x higher throughput than vLLM baselines.

# 2. AI.MAP in Quail

`AI.MAP(input, instruction[, max_tokens])` generates a text answer for each row.

How might one use `AI.MAP` in a SQL query? Imagine a user has a table of agent traces, where each row is a trace: a sequence of messages between a user and an agent, along with the agent's tool calls and their results. Suppose they want to analyze the agent's behavior. Here's an example query they might write:

```sql
SELECT t.id,
       AI.MAP(t.text, 'List the commands the agent ran.') AS commands,
       AI.MAP(t.text, 'Describe the agent''s plan.') AS plan,
       AI.MAP(t.text, 'List the files the agent edited.') AS edits
FROM traces t;
```

This query returns each trace's ID along with three generated fields: the commands the agent ran, a description of its plan, and the files it edited.

`AI.MAP` can also be used in filters, e.g., `WHERE AI.MAP(t.text, 'List the commands the agent ran.') ILIKE '%pytest%'`, but we'll focus on the simpler case of `AI.MAP` projections in this post.

Generally, to execute a query like this with vLLM, you'd create one prompt for each (trace, instruction) pair and pass the prompts to `LLM.generate`. Each prompt contains the trace text followed by the instruction, so the three prompts for a trace share a common prefix (and thereby save computation due to the standard prefix caching optimization<sup><a href="#note-1">1</a></sup> in inference engines):

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen3-4B-FP8",
    enable_prefix_caching=True,
    # Example batch limits; tune for the workload and GPU.
    max_num_seqs=1024,
    max_num_batched_tokens=32768,
)
instructions = [
    "List the commands the agent ran.",
    "Describe the agent's plan.",
    "List the files the agent edited.",
]
prompts = [f"{text}\n\n{inst}" for text in trace_texts for inst in instructions]
outputs = llm.generate(prompts, SamplingParams(temperature=0, max_tokens=256))
```

Each request uses greedy decoding and stops when the model finishes its answer or reaches `max_tokens` (default 256). We also set `max_num_seqs` and `max_num_batched_tokens`, which limit the number of sequences and tokens in each forward pass. These should be tuned for the workload and GPU to avoid underfilling batches and leaving the GPU underutilized.<sup><a href="#note-2">2</a></sup>

# 3. Bulk Decoding Has Different Constraints

Most LLM inference engines are designed for chat, where users care about time to first token (TTFT) and time per output token (TPOT). Bulk decoding has different constraints:

**We don't care when any one request finishes.** We only care about finishing the entire query as quickly as possible. A request can wait until near the end of the query before even beginning its prefill, if doing so improves overall throughput.

**Prompts are typically much longer than outputs.** Each request reads hundreds or thousands of input tokens and usually generates far fewer output tokens. Most of the tokens we process are therefore in prefill, unlike workloads such as coding agents that may generate thousands of output tokens.

These properties let us keep the GPU busy and achieve high throughput through scheduling and attention optimizations alone, without techniques such as speculative decoding<sup><a href="#note-3">3</a></sup> or prefill-decode disaggregation.<sup><a href="#note-4">4</a></sup>

# 4. Query-Aware Scheduling and Attention

Quail takes advantage of two kinds of repetition in `AI.MAP` queries:

1. The same instruction runs over many rows. Quail learns how long each map's outputs tend to be as the query runs, and uses these estimates to decide how much KV memory to reserve when admitting requests into a batch. We call this adaptive admission. It builds on techniques for mixing prefill and decode work, such as Sarathi-Serve.<sup><a href="#note-5">5</a></sup>
2. Multiple maps can read the same document. Rather than reading the document's KV from GPU memory separately for each map, Quail groups these requests and reuses the document's KV within the attention computation, a la Hydragen.<sup><a href="#note-6">6</a></sup>

The CPU prepares batches while the GPU executes the previous batch. Here's the overall execution loop:

## 4.1 Scheduling: Which Requests Should We Admit into a Batch?

Quail tries to keep each forward pass full by mixing prefill and decode work, similar to Sarathi-Serve.<sup><a href="#note-5">5</a></sup> Given a token budget $$B$$, we first schedule one decode token per running request, then fill the remaining budget with prefill chunks from waiting requests (line [6](#map-algorithm-line-6)). We order the waiting requests by document to maximize prefix sharing (see [this post](https://x.com/sh_reya/status/2107875266710409310)).

But how many new requests should we admit? Once a request starts, its KV occupies GPU memory until it finishes or is evicted. For `AI.IF`, we know each request generates one output token, so we can predict its KV memory requirements. For `AI.MAP`, we know the prompt length but not how many output tokens it will generate.

We could allocate KV pages as needed, as vLLM does. We call this *static admission*. But if memory fills up, we may have to evict requests and recompute their KV later. At the other extreme, we could reserve enough pages for the maximum output length, but this would keep other requests out of the batch when outputs are shorter.

**Our approach, *adaptive admission*, is to learn output lengths as the query runs and use these estimates to decide how much KV memory to reserve.** Each map applies the same instruction across many rows, so requests with similar prompt lengths tend to have similar output lengths. For each map $$m$$ and bucket $$b$$ of similar prompt lengths, Quail maintains a survival curve:

$$
S_{m,b}(t) = \Pr(L > t \mid m,b).
$$

Here, $$L$$ is the output length, and $$S_{m,b}(t)$$ is the probability that it exceeds $$t$$ tokens. We update these curves as requests generate tokens or finish, using the Kaplan–Meier estimator.<sup><a href="#note-7">7</a></sup>

At each scheduling round, Quail uses these estimates to choose the *headroom* for every running request: the number of additional KV pages to reserve for future output tokens. Headroom changes as requests generate tokens and the survival curves are updated. These are reservations, not allocations; KV pages are still allocated as tokens are processed.

**How much headroom should we reserve?** Reserving more reduces the risk of eviction and recomputation, but leaves less memory for admitting new requests. We estimate this tradeoff by looking at the next waiting document.

Let $$W$$ be the requests for the maps on that document. Using [roofline estimates]({{ '/blog/ai-filter-cost-estimates/' | relative_url }}), we compare the current batch's average time per token with the time per token if we also admit $$W$$. Multiplying the improvement by $$W$$'s estimated output-token count gives the batching time saved, $$\Delta T_{\mathrm{batch}}$$.

If $$W$$ needs $$P$$ new KV pages for its prompts (after any prefix shared with KV already in memory) and $$H$$ headroom pages, we estimate the batching savings per page as:

$$
c_{\mathrm{page}} = \frac{\Delta T_{\mathrm{batch}}}{P+H}.
$$

We use this page price to choose the headroom $$h$$ for each request $$r$$, minimizing the cost of reserved memory plus expected KV recomputation:

$$
h_r^*(c_{\mathrm{page}}) = \arg\min_{h \geq 0}
\left[
h\,c_{\mathrm{page}} +
\frac{S_r(c_r(h))}{S_r(t_r)}\,R_r(h)
\right].
$$

The first term is the batching savings lost by reserving $$h$$ pages. In the second term, $$S_r$$ is the survival curve associated with request $$r$$, $$t_r$$ is the number of output tokens already generated, and $$c_r(h)$$ is the output length covered by its current pages plus $$h$$ additional pages. The survival-curve ratio estimates the probability that the request outgrows its reservation, conditional on having already generated $$t_r$$ tokens. Multiplying by $$R_r(h)$$, the estimated time to rebuild its KV if evicted, gives the expected recomputation cost. For a new request, $$t_r=0$$ and $$S_r(0)=1$$.

There's one dependency to resolve: the page price depends on the headroom $$H$$ of the next waiting document's requests, but that headroom itself depends on the page price. We use fixed-point iteration:

$$
\begin{aligned}
c_0 &= \Delta T_{\mathrm{batch}}/P, \\
H_k &= \sum_{r\in W} h_r^*(c_k), \\
c_{k+1} &= \frac{\Delta T_{\mathrm{batch}}}{P+H_k}.
\end{aligned}
$$

Starting with a price based on prompt pages alone, we repeatedly compute the headroom for $$W$$ and update the price until $$H_k$$ stops changing. Quail then uses this price to update the headroom of running requests and evaluate new requests for admission.

A new request is admitted if its prompt KV and headroom fit in the available memory, after accounting for the headroom reserved for running requests (line [8](#map-algorithm-line-8)). If its prefix KV is already cached, we reuse those pages. When no documents are waiting, Quail skips the headroom update because there's no competing work to admit.

**Eviction.** Quail can still underestimate output lengths and run out of KV memory. If this happens (line [13](#map-algorithm-line-13)), we evict the request that would otherwise hold the most KV pages for the longest time, relative to the cost of recomputing its KV. Specifically, we use the heuristic:

$$
r^* = \arg\max_{\text{evictable request }r}
\frac{\underbrace{P_r}_{\text{pages freed}}\cdot\underbrace{d_r}_{\text{decode steps left}}}{\underbrace{T_r}_{\text{recompute time}}}.
$$

Here, $$P_r$$ is the number of pages freed, excluding shared pages still needed by other requests; $$T_r$$ is the estimated time to rebuild the request's KV; and $$d_r$$ is its estimated remaining decode steps. We estimate $$d_r$$ from the learned survival curve:

$$
d_r = \sum_{u=t_r}^{M_r-1}\frac{S_r(u)}{S_r(t_r)}.
$$

The sum runs up to the request's output-token limit $$M_r$$, given the $$t_r$$ tokens already generated.

Interestingly, under our scheduling model, an optimal schedule never needs to evict an in-progress request, even in this high-throughput setting. This might sound obvious, but it wasn't to Shreya! We'll save the proof for the paper.

## 4.2 Forward Pass: Reading Each Document's KV Once

After we've packed a batch, the question is how to execute its forward pass on the GPU (line [11](#map-algorithm-line-11)). This is straightforward if a query has a single `AI.MAP`: we use standard FlashAttention. But if a query has multiple maps, line [1](#map-algorithm-line-1) orders requests so maps on the same document are grouped together. A batch can therefore contain requests that share a document.

If a batch contains requests that share a document, we don't need to load that document's KV from GPU memory (HBM) into on-chip SRAM separately for each request. We use Hydragen-style attention<sup><a href="#note-6">6</a></sup> to load a KV tile once and reuse it across those requests. We compute attention to each request's instruction and generated output separately, then merge the results.

During query planning, Quail uses roofline estimates to choose between standard FlashAttention and shared-prefix attention, including the cost of the extra attention call and merge.

# 5. Experiments

We'll start with our [setup](#51-setup): the model, the queries, and the systems we compare. Then we'll look at [how fast Quail runs `AI.MAP` queries](#52-how-fast-is-aimap) compared with vLLM, [whether we actually need adaptive admission](#53-do-we-need-adaptive-admission), and [what Quail's scheduler learns](#54-what-does-the-scheduler-learn) while a query runs.

## 5.1 Setup

We run all experiments with Qwen3 4B (FP8) on one H100, and let each map write up to 1,024 output tokens. We use three queries from [QUAIL-B](https://github.com/fsdatalab/quail-bench), our benchmark of SQL queries with AI functions. In all three, each `AI.MAP` is a projection, not an aggregation: it writes one new column with one output per row, as in `SELECT c.id, AI.MAP(c.text, 'List the parties to this contract and the role of each.') AS parties FROM contracts c`. The queries are:

- **CUAD-21** runs 3 maps on each of 224 legal contracts, which are about 7,200 tokens each: list every obligation and who it binds, rewrite the key terms in plain English, and list every defined term with its definition.
- **CUAD-22** runs 16 maps on the same contracts. Each map covers one part of the contract, e.g., listing the parties, quoting the termination clauses, or summarizing each section in one sentence. Comparing CUAD-22 with CUAD-21 shows what happens when each document has many more maps.
- **AGENT-6** runs 3 maps on 1,772 snapshots of agent traces, which are about 9,700 tokens each: list the commands the agent ran, describe the agent's plan and how it changed, and list the files the agent edited.

For each query, we report throughput (input and output tokens per second) and KV regret (the tokens computed beyond the fewest the query needs).

We compare Quail, as described in [Section 4](#4-query-aware-scheduling-and-attention), with two vLLM baselines:

- **Stock vLLM.** We compile each query into LLM calls: one call for every map on every document. Then we pass all of the calls to `LLM.generate` in one batch, in random order.
- **vLLM-sorted.** Same as stock vLLM, but we sort the calls so that all of the calls on one document are next to each other. This way, vLLM's prefix caching can reuse each document's KV, which reduces KV regret.

## 5.3 Do We Need Adaptive Admission?

Recall that Quail decides how much KV to reserve for each request using [adaptive admission](#41-scheduling-which-requests-should-we-admit-into-a-batch). Do we really need this machinery, or could we get away with only the [shared-prefix attention](#42-forward-pass-reading-each-documents-kv-once)? To find out, we compare Quail with a version that uses the same attention but static admission: it reserves KV only for each request's prompt, as vLLM does.

With adaptive admission, Quail evicts 13–20x fewer requests on the two CUAD queries, and none at all on AGENT-6 ([Figure 4](#figure-4)). On CUAD-22, this makes the query 1.35x faster. On CUAD-21 and AGENT-6, the speedup is smaller: 1.05x and 1.06x, respectively.

## 5.4 What Does the Scheduler Learn?

So we're sold on adaptive admission. But what does it actually learn? Quail learns one survival curve for each map and each bucket of similar prompt lengths. [Figure 5](#figure-5) shows, for each map, the curve for the most common bucket in each query, at the end of the run.

<img src="{{ '/assets/blog/ai-map/survival-curves.svg' | relative_url }}" alt="Learned survival curves for each map, for the most common document length in each query. On CUAD-22, parties finishes first and notices runs longest. On CUAD-21, plain terms finishes much earlier than obligations, which mostly runs to the 1,024-token limit. On AGENT-6, edits and plan finish earlier than commands.">
<figcaption>Figure 5. Learned survival curves: the share of outputs still being written after each number of output tokens, for each map, for the most common document length in each query. On CUAD-22, only the shortest and longest of the 16 maps are labeled.</figcaption>
</figure>

First, output lengths vary a lot from map to map, even on documents of the same length. On CUAD-21, 70% of "plain terms" outputs end within 800 tokens, while 95% of "obligations" outputs are still being written at the 1,024-token limit. On CUAD-22, the 16 maps spread across the whole range: 77% of "parties" outputs end within 400 tokens, while 77% of "notices" outputs hit the limit.

Second, the longer the prompt, the more headroom Quail reserves ([Figure 6](#figure-6)). As described in [Section 4.1](#41-scheduling-which-requests-should-we-admit-into-a-batch), if a request is evicted, its prompt has to be computed again, which costs more for a longer prompt.

We find that Quail reserves almost nothing extra for prompts under 1,000 tokens, but room for 400–900 output tokens for prompts of 8,000 tokens or more.

The top panel shows the headroom: the KV pages Quail has reserved for outputs but not yet filled. It rises when Quail admits new requests, and falls as those requests generate output tokens. The bottom panel shows how many requests are decoding. At the start, no output has finished, so Quail underestimates output lengths and admits many requests at once. These requests start together and most stop at the 1,024-token limit, so they also finish together, near step 1,000. After that, Quail admits fewer requests at a time, each time earlier requests finish (the green ticks). The requests start at different times, so the waves get smaller. Near the end, only a few documents are still waiting, so Quail reserves less headroom, and more requests can run at once.

Overall, Quail processes 2.1–6.2x more tokens per second than stock vLLM on our map queries. Interestingly, while adaptive admission reduces evictions by 13–20x, it improves throughput by only 1.05–1.35x over static admission. Unlike in traditional databases, where page evictions can trigger expensive disk reads,<sup><a href="#note-9">9</a></sup> the cost of recomputing evicted KV is relatively small compared to the cost of executing the entire query. In other words, avoiding KV recomputation is less valuable than, simply, improving GPU utilization across the query.



# 6. Conclusion

In this post, we looked at how to make bulk text generation faster with `AI.MAP`. Unlike filters and classifiers, which typically generate only a few tokens, maps can generate any number of tokens per row. As the query runs, Quail learns how long each map's outputs tend to be and uses this to decide how much KV memory to reserve. And when multiple maps read the same document, Quail avoids redundant memory reads by sharing the document's KV during attention. Together, these optimizations let Quail process 2.1–6.2x more tokens per second than stock vLLM on our queries.

With `AI.MAP`, Quail now supports four kinds of AI functions in SQL: [filters and joins]({{ '/blog/introducing-quail/' | relative_url }}) with `AI.IF`, [classification]({{ '/blog/ai-classification/' | relative_url }}) with `AI.CLASSIFY`, [extraction]({{ '/blog/ai-extract/' | relative_url }}) with `AI.EXTRACT`, and now generation with `AI.MAP`. Try out [Quail](https://github.com/fsdatalab/quail), and if you like what we're building, give it a star on GitHub!
