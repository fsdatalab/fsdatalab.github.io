<aside class="tldr"><strong>TL;DR:</strong> How do you run LLM-powered text generation over an entire dataset, as fast as possible? Our implementation of <code>AI.MAP</code> in Quail achieves <strong>2.1–6.2× higher throughput</strong> than stock vLLM on the same model and GPU. **Outline draft.** Hook for the tweet / first line: Summarizing a dataset with an LLM is slow, in part because existing inference engines are built for low-latency chat applications. We changed how the engine schedules work and made it up to 6× faster on the same model and GPU, with no training.

# 1. Introduction

- People often want to generate text in bulk: for example, summarize each contract in a dataset, or describe what an agent did or what the user asked for in each agent trace.
- In inference-speak, you can think of this workload as "bulk decode": a user wants to run an LLM on every row of their dataset, which may have tens of thousands of rows or more.
- Users can express such queries in Quail, our inference engine for SQL with AI functions, with the `AI.MAP` function.
- You might expect bulk decoding to be slow and to leave the GPU idle, since each decoded token needs its own forward pass. This may be true if you consider each row an individual inference request, but our key insight is that we can trade off latency on individual rows to improve throughput across the dataset.
- We'll go through: what `AI.MAP` is, how bulk decoding differs from chat, Quail's novel optimizations, and experiments demonstrating up to 6.2× higher throughput than stock vLLM.

# 2. AI.MAP in Quail

`AI.MAP(input, instruction[, max_tokens])` generates a text answer for each row.

How might one use `AI.MAP` in a SQL query? Imagine a user has a table of agent traces, where each row is a trace: a sequence of messages between a user and an agent, along with the agent's tool calls and their results. Suppose they want to analyze the agent's behavior. Here's an example query they might write:

```sql
SELECT t.id,
       AI.MAP(t.text, 'List the commands the agent ran.') AS commands,
       AI.MAP(t.text, 'Describe the agent''s plan.') AS plan,
       AI.MAP(t.text, 'List the files the agent edited.') AS edits
FROM traces t;
```

This query returns each trace's ID along with three generated fields: the commands the agent ran, a description of its plan, and the files it edited.

`AI.MAP` can also be used in filters, e.g., `WHERE AI.MAP(t.text, 'List the commands the agent ran.') ILIKE '%pytest%'`, but we'll focus on the simpler case of `AI.MAP` projections in this post.

Generally, to execute a query like this with vLLM, you'd create one prompt for each (trace, instruction) pair and pass the prompts to `LLM.generate`. Each prompt contains the trace text followed by the instruction, so the three prompts for a trace share a common prefix (and thereby save computation due to the standard prefix caching optimization<sup><a href="#note-1">1</a></sup> in inference engines):

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen3-4B-FP8",
    enable_prefix_caching=True,
    # Example batch limits; tune for the workload and GPU.
    max_num_seqs=1024,
    max_num_batched_tokens=32768,
)
instructions = [
    "List the commands the agent ran.",
    "Describe the agent's plan.",
    "List the files the agent edited.",
]
prompts = [f"{text}\n\n{inst}" for text in trace_texts for inst in instructions]
outputs = llm.generate(prompts, SamplingParams(temperature=0, max_tokens=256))
```

Each request uses greedy decoding and stops when the model finishes its answer or reaches `max_tokens` (default 256). We also set `max_num_seqs` and `max_num_batched_tokens`, which limit the number of sequences and tokens in each forward pass. These should be tuned for the workload and GPU to avoid underfilling batches and leaving the GPU underutilized.<sup><a href="#note-2">2</a></sup>

# 3. Bulk Decoding Has Different Constraints

Beyond standard optimizations such as prefix caching, continuous batching, and paged attention, two active areas of inference research are:

- **Speculative decoding:** uses a smaller, faster draft model to guess several future tokens at once, which the main (target) model verifies in a single parallel step.<sup><a href="#note-3">3</a></sup>
- **Prefill-decode disaggregation:** separates the compute-heavy prefill phase and memory-bound decode phase onto different specialized GPUs or nodes connected via high-speed networking like RDMA.<sup><a href="#note-4">4</a></sup>

Both target low-latency serving, where each decode batch processes one token from each of many requests. Even with batching, decoding is often memory-bound: the GPU spends more time reading weights and KV vectors than doing arithmetic.

But we can keep the GPU compute-bound and get high throughput without speculative decoding or prefill-decode disaggregation, because two things about our workload are different:

**We don't care when any one request finishes.** In chat, each request needs a low time to first token (TTFT) and a low time per output token (TPOT). In contrast, in Quail, we just want to finish the entire query as fast as possible. We are happy to let a request wait until near the end of the query before even beginning its prefill.

**The prompt is almost always much longer than the output.** Data processing, by definition, involves processing some data: each request reads hundreds or thousands of input tokens and typically generates far fewer output tokens. Most of the tokens we compute are therefore in prefill, the initial forward pass over the prompt. This differs from coding agents, which may generate thousands of output tokens from a shorter prompt.

These properties give us the freedom to schedule and execute LLM requests in Quail differently!

# 4. Quail's Secret Sauce

Our key insight is to plan requests across the query and optimize their execution on the GPU:

1. **Plan and schedule the work:** building on prior work such as Sarathi-Serve,<sup><a href="#note-5">5</a></sup> which advocates mixing prefill chunks with decode tokens, we introduce a simple, *adaptive* packing algorithm that keeps forward passes full, while minimizing evictions of KV we'll need again (Section 4.1).
2. **Optimize the forward pass for the data at hand:** when several maps read the same document, run them together and reuse the document's KV within the attention computation, a la Hydragen<sup><a href="#note-6">6</a></sup> (Section 4.2).

The CPU schedules requests and prepares batches; the GPU executes their forward passes. These overlap: while the GPU runs one batch, the CPU prepares the next. At a high level:

## 4.1 Scheduling: Which Requests Should We Admit into a Batch?

Our packing algorithm tries to fill each forward pass while leaving enough KV memory for requests to keep decoding. Given a token budget $$B$$, we first take one decode token per ongoing request, then fill the remaining space with prefill work from the waiting queue (line [6](#map-algorithm-line-6)). We order that queue to maximize prefix sharing (see [this post](https://x.com/sh_reya/status/2107875266710409310) for details).

**At the outset of a request, how much KV should we set aside?** For `AI.IF`, we know the request will generate one output token, so we can reserve exactly enough memory. For `AI.MAP`, we know the prompt length but not how long we need to keep decoding.

At one extreme, we could allocate pages only for the prompt's KV, as vLLM does, then add pages as needed during decoding. But when the KV memory is full, we have to evict requests and recompute their KV later.

At the other extreme, we could reserve pages for the prompt plus the maximum output length—256 tokens in our example. This avoids eviction, but can leave batches underfull when outputs are shorter.

This recomputation contributes to *KV regret*: all token computation beyond the minimum needed for the query, including repeated prefills of shared document prefixes.

**Our key insight is to learn output lengths as the query runs.** Each `AI.MAP` applies the same task to all rows, so requests with similar prompt lengths are likely to have similar output lengths. For each map $$m$$ and prompt-length bucket $$b$$, we learn a survival curve:

$$
S_{m,b}(t) = \Pr(L > t \mid m,b).
$$

Here, $$L$$ is the output length and $$S_{m,b}(t)$$ is the probability that it exceeds $$t$$ output tokens. As requests generate tokens or finish, we update the curves with these new observations using the Kaplan–Meier estimator.<sup><a href="#note-7">7</a></sup>

Then, how do we use these estimates to determine the *headroom*—the additional output pages to reserve when first admitting request $$r$$ into a batch (line [7](#map-algorithm-line-7))? Let $$h$$ be that page count. We want to minimize the extra execution time from keeping other requests out of the batch and rebuilding request $$r$$'s KV if it later runs out of memory.

First, we estimate the cost of keeping a page reserved. Let $$W$$ be the next waiting document's requests. Using [roofline estimates](https://fsdatalab.github.io/blog/ai-filter-cost-estimates/), we compare the current batch's average time per token with the extra time per token needed to add $$W$$. Any reduction, multiplied by $$W$$'s estimated output-token count, gives the batching time saved, $$\Delta T_{\mathrm{batch}}$$.

If $$W$$ needs $$P$$ prompt pages and $$H$$ output headroom pages, the savings per page is:

$$
c_{\mathrm{page}} = \frac{\Delta T_{\mathrm{batch}}}{P+H}.
$$

For a fixed page cost $$c_{\mathrm{page}}$$, we choose:

$$
h_r^*(c_{\mathrm{page}}) = \arg\min_{h \geq 0}
\left[h\,c_{\mathrm{page}} + \frac{S_r(c_r(h))}{S_r(t_r)}\,R_r(h)\right].
$$

The first term, $$h\,c_{\mathrm{page}}$$, is the batching savings we give up by keeping $$h$$ pages reserved. For the second term, $$S_r$$ is request $$r$$'s learned survival curve, $$c_r(h)$$ is the output length covered by its current pages plus $$h$$ more, and $$t_r$$ is the output tokens generated so far. $$S_r(c_r(h))/S_r(t_r)$$ estimates the probability that request $$r$$ outgrows that reservation. Multiplying by $$R_r(h)$$, the estimated time to rebuild its KV if evicted, gives the expected recomputation time. For a new request, $$t_r=0$$ and $$S_r(0)=1$$.

We use *fixed-point iteration* to find a page cost consistent with the headroom it induces. Let $$c_k$$ be the page cost and $$H_k$$ the total headroom at update $$k$$:

$$
\begin{aligned}
c_0 &= \Delta T_{\mathrm{batch}}/P, \\
H_k &= \sum_{r\in W} h_r^*(c_k), \\
c_{k+1} &= \frac{\Delta T_{\mathrm{batch}}}{P+H_k}.
\end{aligned}
$$

1. **Start:** price pages using only the prompt-page count $$P$$.
2. **Choose headroom:** apply the reservation rule at price $$c_k$$ to each request in $$W$$, then sum to get $$H_k$$.
3. **Update the price:** divide the same batching savings by $$P+H_k$$. Repeat steps 2–3 until $$H_k$$ stops changing. If no requests are waiting, the page cost is zero.

So, we admit request $$r$$ into a batch if its prompt KV and estimated headroom fit in free memory after existing reservations (line [8](#map-algorithm-line-8)). If its prefix KV is already cached, we reuse those pages instead of reserving them again.

**Eviction.** Of course, we may underestimate how long a request will keep decoding. If we run out of KV memory (line [13](#map-algorithm-line-13)), we evict the request that is cheapest to recompute relative to how many KV pages it would free, as well as how much longer it is likely to keep decoding. We choose request $$r^*$$ by minimizing:

$$
r^* = \arg\min_{\text{evictable request }r}
\frac{\underbrace{T_r}_{\text{recompute time}}}
{\underbrace{P_r}_{\text{pages freed}}\;\cdot\;\underbrace{d_r}_{\text{decode steps left}}}.
$$

Here, $$T_r$$ is the estimated time to rebuild request $$r$$'s KV, and $$P_r$$ excludes shared pages another request still needs. We estimate the remaining decode steps $$d_r$$ from the survival curve:

$$
d_r = \sum_{u=t_r+1}^{M_r}\frac{S_r(u)}{S_r(t_r)}.
$$

The sum ranges over future output lengths $$u$$ up to request $$r$$'s output limit $$M_r$$, given the $$t_r$$ tokens already generated.

Interestingly, under our scheduling model, an optimal schedule never needs to evict an in-progress request, even in this high-throughput setting. This might sound obvious, but it wasn't to Shreya! We'll save the proof for the paper.

## 4.2 Forward Pass: Reading Each Document's KV Once

After we've packed a batch, the question is how to execute its forward pass on the GPU (line [11](#map-algorithm-line-11)). This is straightforward if a query has a single `AI.MAP`: we use standard FlashAttention. But if a query has multiple maps, line [1](#map-algorithm-line-1) orders requests so maps on the same document are grouped together. A batch can therefore contain requests that share a document.

If a batch contains requests that share a document, we don't need to load that document's KV from GPU memory (HBM) into on-chip SRAM separately for each request. We use Hydragen-style attention<sup><a href="#note-6">6</a></sup> to load a KV tile once and reuse it across those requests. We compute attention to each request's instruction and generated output separately, then merge the results.

## 5.3 Do We Need Adaptive Headroom?

- Could we get away with just the shared-prefix attention from Section 4.2? Compare two Quail runs with the same attention path: one reserves only for prefill, and the other uses the adaptive headroom from Section 4.1.
- For CUAD-22, with 16 maps per contract, prompt-only reservation takes 345 seconds and causes 2,012 evictions. Adaptive headroom takes 255 seconds with 103 evictions: 1.35× faster and about 95% fewer evictions.
- Faster attention does not prevent requests from running out of KV memory. This comparison shows why the packing algorithm matters: avoiding evictions means less KV to rebuild.
- Show all three queries. The query-time improvement is smaller on CUAD-21 (161 to 153 seconds) and AGENT-6 (783 to 740 seconds), although evictions fall on both.
