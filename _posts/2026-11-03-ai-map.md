**Outline draft.** Hook for the tweet / first line: Summarizing a dataset with an LLM is slow, in part because existing inference engines are built for low-latency chat applications. We changed how the engine schedules work and made it up to 6× faster on the same model and GPU, with no training.

# 1. Introduction

- Lots of AI-powered data processing involves some form of "bulk" text generation: e.g., in a dataset of contracts, summarize each contract; in a dataset of agent traces, describe what an agent did or what the user asked for.
- In inference-speak, you can think of this workload as "bulk decode": a user wants to run an LLM on every row of their dataset, which may have tens of thousands of rows or more.
- Users can express such queries in Quail, our inference engine for SQL with AI functions, with the `AI.MAP` function. In this post, we dive into how Quail executes them.
- You might expect bulk decoding to be slow and to leave the GPU idle, since each decoded token needs its own forward pass. But we will find that bulk decoding is not chat, and with the right scheduling, Quail can keep the GPU busy.
- We'll go through: what `AI.MAP` is, how bulk decoding differs from chat, Quail's novel optimizations, and experiments demonstrating up to 6.2× higher throughput than stock vLLM.

# 2. AI.MAP in Quail

`AI.MAP(input, instruction[, max_tokens])` writes one text answer per row. For example, AGENT-6 asks three questions of each agent trace:

```sql
SELECT s.id,
       AI.MAP(s.text, 'List the commands the agent ran.') AS commands,
       AI.MAP(s.text, 'Describe the agent''s plan.') AS plan,
       AI.MAP(s.text, 'List the files the agent edited.') AS edits
FROM snapshots s;
```

*(Swap in AGENT-6's real instructions.)*

How it becomes LLM requests:

- One request per row and map: the document, then the instruction. The LLM writes greedily until it stops or hits `max_tokens` (default 256).
- Maps on the same row share the document as a prefix. So a row with three maps is three requests with the same long start.
- A map after a filter only runs on the rows that pass.

For example, if we ran the query above in vLLM, we'd do:

```python
from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen3-4B-FP8", enable_prefix_caching=True)
instructions = [
    "List the commands the agent ran.",
    "Describe the agent's plan.",
    "List the files the agent edited.",
]
# One prompt per (row, map); a row's three prompts share the document.
prompts = [f"{doc}\n\n{inst}" for doc in snapshots for inst in instructions]
outputs = llm.generate(prompts, SamplingParams(temperature=0, max_tokens=256))
```

With 1,772 snapshots, that is 5,316 requests in one call.

# 3. Bulk Decoding Is Not Chat

- The main recent optimization for decoding in serving engines is prefill-decode (PD) disaggregation: run prefill and decode on separate GPUs. It makes sense for chat, where every user needs their first token fast and then a steady stream after.
- But if we squint at our workload, two things are different:
  - **We don't care when any one answer finishes.** Only the whole query's time matters. It is fine to wait until the end to run some requests.
  - **The prompt is almost always much longer than the answer.** Documents run thousands of tokens; answers, a few hundred.
- So instead of separating prefill and decode, we want to mix them, and keep every forward pass full.

# 4. Quail's Secret Sauce

At a high level, Quail fills each forward pass with decode tokens from running answers and prefill tokens from new documents (like Sarathi-Serve's chunked prefill). It also runs all the maps on a document side by side, so they share the document's KV. On top of that, there are tricks on the planning side and on the forward pass side.

## 4.1 Planning: How Much KV to Set Aside for an Answer

- We don't know how long an answer will be. vLLM sets aside pages for the prompt only, and evicts answers when memory runs out. The other extreme, setting aside pages for `max_tokens`, leaves passes half empty.
- Quail watches answers finish as the query runs, and learns how long each map's answers tend to be. For each new answer, it sets aside enough pages that the answer will rarely run out, but not so many that pages sit empty.
- If we do need to evict, Quail picks the answer that will hold the most pages for the longest, per second of recompute. vLLM evicts the most recently scheduled request.

## 4.2 Forward Pass: Reading Each Document's KV Once

- Long prompts make every decode token expensive, because each one rereads the whole prompt's KV.
- Prefix caching in vLLM and SGLang stores the shared document KV once, but every request still reads it separately. With 16 maps on one contract, that is 16 reads per pass.
- Quail uses Hydragen-style attention: the maps on a document read its KV together, once per pass, and then merge with their own answer's attention.
- With one map, there is nothing to share, and the extra kernels only cost time. So Quail falls back to plain FlashAttention. The planner picks the attention path from measured costs and the workload.
- We see an exciting opportunity here: a declarative kernel stack for LLM-powered data processing, where the planner picks kernels the way a database picks join algorithms.

# 5. Experiments

Three map queries on Qwen3 4B FP8, one H100. Quail processes 2.1–6.2× more tokens per second than stock vLLM.

<figcaption>Figure 1. Input and output tokens per second on three map queries. Multipliers are over stock vLLM.</figcaption>

- Stock vLLM gets the requests in random order. A document's maps land far apart, so its cached KV is often evicted before the next map reads it.
- Sorting requests by document gets vLLM to 1.7–2.5× over stock. Quail gets 2.1–6.2×, the most with 16 maps per document.
- That puts Quail at 51–66% of the speed of light: an estimate of the best any engine could do on one H100 with unlimited KV (220k, 63k, and 111k tokens per second on CUAD-22, CUAD-21, and AGENT-6).

- Random order computes 4–5× more tokens than needed. Sorting cuts that to 6–29%. Quail computes only 1–4% extra.

- Evictions are one part of KV regret. Sorted vLLM runs more answers at once, so it evicts the most: 2,680 on CUAD-22. Quail evicts 0–103.
- Ablation for 4.1: with pages set aside for the prompt only, CUAD-22 has 2,012 evictions and takes 345 s. With Quail's estimate, it has 103 evictions and takes 255 s.

*Notes for the draft:* throughput is every prompt's full length plus every answer token, divided by query time: about 28.5M tokens for CUAD-22, 5.4M for CUAD-21, and 54.0M for AGENT-6. All three systems are given Quail's answer token count. vLLM's regret is approximate, because the minimum uses Quail's answer lengths. vLLM's trace for CUAD-21 was not saved.
