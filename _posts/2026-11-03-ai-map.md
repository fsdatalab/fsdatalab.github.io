# 1. Introduction

People often want to generate text in bulk: for example, summarize every contract in a dataset, or describe what an agent did in each of thousands of agent traces. In LLM inference, this is called *bulk decoding*: an LLM generates text for every row of a dataset, which can have tens of thousands of rows. In Quail, our inference engine for SQL queries with AI functions, users express these workloads with the `AI.MAP` function.

Bulk decoding can be slow, since generating each output token requires a forward pass through the model. But unlike chat, where latency matters for _each_ request, we only care about finishing the entire query (a group of requests) as quickly as possible. This lets us trade off latency on individual rows for higher throughput across the dataset.

In this post, we'll explain how `AI.MAP` works, how Quail optimizes bulk decoding, and why these optimizations achieve up to 6.2x higher throughput than vLLM baselines.

# 2. AI.MAP in Quail

`AI.MAP(input, instruction[, max_tokens])` generates a text answer for each row.

How might one use `AI.MAP` in a SQL query? Imagine a user has a table of agent traces, where each row is a trace: a sequence of messages between a user and an agent, along with the agent's tool calls and their results. Suppose they want to analyze the agent's behavior. Here's an example query they might write:

```sql
SELECT t.id,
       AI.MAP(t.text, 'List the commands the agent ran.') AS commands,
       AI.MAP(t.text, 'Describe the agent''s plan.') AS plan,
       AI.MAP(t.text, 'List the files the agent edited.') AS edits
FROM traces t;
```

This query returns each trace's ID along with three generated fields: the commands the agent ran, a description of its plan, and the files it edited.

`AI.MAP` can also be used in filters, e.g., `WHERE AI.MAP(t.text, 'List the commands the agent ran.') ILIKE '%pytest%'`, but we'll focus on the simpler case of `AI.MAP` projections in this post.

Generally, to execute a query like this with vLLM, you'd create one prompt for each (trace, instruction) pair and pass the prompts to `LLM.generate`. Each prompt contains the trace text followed by the instruction, so the three prompts for a trace share a common prefix (and thereby save computation due to the standard prefix caching optimization<sup><a href="#note-1">1</a></sup> in inference engines):

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen3-4B-FP8",
    enable_prefix_caching=True,
    # Example batch limits; tune for the workload and GPU.
    max_num_seqs=1024,
    max_num_batched_tokens=32768,
)
instructions = [
    "List the commands the agent ran.",
    "Describe the agent's plan.",
    "List the files the agent edited.",
]
prompts = [f"{text}\n\n{inst}" for text in trace_texts for inst in instructions]
outputs = llm.generate(prompts, SamplingParams(temperature=0, max_tokens=256))
```

Each request uses greedy decoding and stops when the model finishes its answer or reaches `max_tokens` (default 256). We also set `max_num_seqs` and `max_num_batched_tokens`, which limit the number of sequences and tokens in each forward pass. These should be tuned for the workload and GPU to avoid underfilling batches and leaving the GPU underutilized.<sup><a href="#note-2">2</a></sup>

# 3. Bulk Decoding Has Different Constraints

Most LLM inference engines are designed for chat, where users care about time to first token (TTFT) and time per output token (TPOT). Bulk decoding has different constraints:

**We don't care when any one request finishes.** We only care about finishing the entire query as quickly as possible. A request can wait until near the end of the query before even beginning its prefill, if doing so improves overall throughput.

**Prompts are typically much longer than outputs.** Each request reads hundreds or thousands of input tokens and usually generates far fewer output tokens. Most of the tokens we process are therefore in prefill, unlike workloads such as coding agents that may generate thousands of output tokens.

These properties let us keep the GPU busy and achieve high throughput through scheduling and attention optimizations alone, without techniques such as speculative decoding<sup><a href="#note-3">3</a></sup> or prefill-decode disaggregation.<sup><a href="#note-4">4</a></sup>

# 4. Query-Aware Scheduling and Attention

Each `AI.MAP` expression in a query is a *map*, and applying it to one row produces a *request*. In the trace query from [Section 2](#2-aimap-in-quail), each trace produces three requests that read the same text. Quail exploits two properties of this workload: it can learn output lengths from running the same map over many rows, and it can share KV reads when multiple maps use the same document.

The CPU builds batches of requests, and the GPU executes one forward pass per batch. At a high level, the execution loop is:

<pre><code><span class="algorithm-line" id="map-algorithm-line-1" data-line="1"><strong>while</strong> unfinished requests remain:</span>
<span class="algorithm-line" id="map-algorithm-line-2" data-line="2">    release the KV of finished requests</span>
<span class="algorithm-line" id="map-algorithm-line-3" data-line="3">    grow running requests' KV; <strong>if</strong> KV memory is full: evict</span>
<span class="algorithm-line" id="map-algorithm-line-4" data-line="4">    batch = decode tokens of running requests + KV rebuilds of evicted requests</span>
<span class="algorithm-line" id="map-algorithm-line-5" data-line="5">    update estimates of output lengths and headroom</span>
<span class="algorithm-line" id="map-algorithm-line-6" data-line="6">    <strong>for each</strong> waiting document, <strong>while</strong> batch size &lt; token budget:</span>
<span class="algorithm-line" id="map-algorithm-line-7" data-line="7">        <strong>if not</strong> <a class="map-planning-call" href="#41-scheduling-which-requests-should-we-admit-into-a-batch" title="Adaptive admission (Section 4.1)">worth_admitting</a>(document): <strong>break</strong></span>
<span class="algorithm-line" id="map-algorithm-line-8" data-line="8">        admit its requests and reserve their headroom</span>
<span class="algorithm-line" id="map-algorithm-line-9" data-line="9">        add a chunk of its prefill to the batch</span>
<span class="algorithm-line" id="map-algorithm-line-10" data-line="10">    <a class="map-execution-call" href="#42-forward-pass-reading-each-documents-kv-once" title="GPU execution (Section 4.2)">gpu.submit</a>(batch)</span></code></pre>
</div>

[Section 4.1](#41-scheduling-which-requests-should-we-admit-into-a-batch) explains how Quail builds each batch (lines [2](#map-algorithm-line-2)–[9](#map-algorithm-line-9)); [Section 4.2](#42-forward-pass-reading-each-documents-kv-once) explains how Quail executes the forward pass (line [10](#map-algorithm-line-10)).

## 4.1 Scheduling: Which Requests Should We Admit into a Batch?

Quail mixes prefill and decode work in each forward pass, building on Sarathi-Serve.<sup><a href="#note-5">5</a></sup> Each batch has a token budget, derived from the GPU's hardware specs. Quail first schedules one decode token per running request (line [4](#map-algorithm-line-4)), then fills the rest of the budget with prefill chunks from waiting documents (lines [6](#map-algorithm-line-6) and [9](#map-algorithm-line-9)). Waiting documents are ordered to maximize prefix sharing (see [this post](https://x.com/sh_reya/status/2107875266710409310)).

**Headroom.** A simple admission policy, as in vLLM, starts requests whenever their prompts fit in KV memory and allocates additional KV pages as output tokens are generated. But `AI.MAP` outputs have unknown lengths. Starting too many requests can exhaust KV memory, forcing Quail to evict requests and recompute their KV later. Instead, Quail accounts for future output growth before admitting a document's map requests. We call the extra KV pages reserved for unfinished outputs *headroom*. Headroom reduces the risk of eviction, but also limits the memory available for new requests. The reserved pages are allocated only when decoding actually needs them. When a request finishes, Quail releases its KV, including any reserved pages it never used (line [2](#map-algorithm-line-2)).

**Estimating output lengths.** Each map applies the same instruction to many rows, so Quail learns a survival curve for each map $$m$$ and bucket $$b$$ of similar prompt lengths:

$$
S_{m,b}(t) = \Pr(L > t \mid m,b).
$$

Here, $$L$$ is the output length, and the curve estimates the probability that an output exceeds $$t$$ tokens. Before each batch, Quail updates the curves as requests generate tokens or finish (line [5](#map-algorithm-line-5)), using the Kaplan–Meier estimator.<sup><a href="#note-6">6</a></sup> For any proposed headroom, Quail estimates the probability that a request outgrows the reserved pages and multiplies it by the cost of recomputing the request's KV. The result is an expected recomputation time for each headroom choice.

**Admission.** Before each forward pass while documents are waiting, Quail updates its estimates of output lengths and chooses headroom for running requests (line [5](#map-algorithm-line-5)). Then it considers the next waiting document (line [7](#map-algorithm-line-7)), meaning all the map requests associated with one input row. Quail compares the minimum expected recomputation time under two choices: leave the document's requests waiting, or admit them and redistribute headroom within the available KV memory. The calculation counts only new physical KV pages: cached prefixes do not need to be allocated again.

Quail uses [roofline estimates]({{ '/blog/ai-filter-cost-estimates/' | relative_url }}) to predict the batching time saved by admitting the document's requests. Admission proceeds when the predicted time saving exceeds the additional expected recomputation time. Quail repeats the comparison for each subsequent waiting document, updating available memory and headroom after every admission (line [8](#map-algorithm-line-8)). It stops at the first document it does not admit, so documents start in order.

**Eviction.** If Quail knew every output length in advance, it would never need to evict: some optimal schedule runs each request to completion once it starts. But Quail only estimates output lengths --- imperfectly, so a request can still outgrow its headroom. What should Quail evict when this happens? If KV memory fills up (line [3](#map-algorithm-line-3)), Quail scores each running request by the KV pages its eviction would free, times the decode steps those pages would otherwise stay in use, divided by the time to rebuild its KV later. Quail evicts the request with the highest score:

$$
\text{eviction score} = \frac{\text{pages freed} \times \text{expected decode steps left}}{\text{time to rebuild KV}}.
$$

The page count excludes shared KV pages still needed by other requests, and the remaining decode steps are estimated from the survival curve. An evicted request waits in a queue, and Quail rebuilds its KV in later batches (line [4](#map-algorithm-line-4)).

## 4.2 Forward Pass: Reading Each Document's KV Once

The second optimization reduces KV memory reads within a forward pass. A batch may contain several requests for the same document. Standard prefix caching avoids recomputing their shared KV, but standard FlashAttention still loads that KV from GPU memory (HBM) into on-chip SRAM separately for each request.

Quail avoids these repeated reads with shared-prefix attention, as in Hydragen.<sup><a href="#note-7">7</a></sup> It loads each tile of the document's shared KV once and uses it for all the requests in the group. Attention to each request's own instruction and generated output is computed separately, then merged with the shared-prefix result.

<figure id="figure-2" style="width: min(48rem, calc(100vw - 3rem));">
<img src="{{ '/assets/blog/ai-map/attention-reads.svg' | relative_url }}" alt="Left, standard attention: one tile of the trace KV in HBM is copied into SRAM three times, once for each of three maps. Right, shared-prefix attention: the tile is copied into SRAM once and used by all three maps.">
<figcaption>Figure 2. One decode step of the three maps in our trace query. Standard attention loads each tile of trace KV from HBM into SRAM once per map. Shared-prefix attention loads the tile once for all three maps, then merges the result with attention over each map's own instruction and output.</figcaption>
</figure>

Shared-prefix attention adds an extra attention call and merge. During query planning, Quail uses roofline estimates to choose between standard FlashAttention and shared-prefix attention.

# 5. Experiments

We'll start with our [setup](#51-setup): the model, the queries, and the systems we compare. Then we'll look at [how fast Quail runs `AI.MAP` queries](#52-how-fast-is-aimap) compared with vLLM, [whether we actually need adaptive admission](#53-do-we-need-adaptive-admission), and [what Quail's scheduler learns](#54-what-does-the-scheduler-learn) while a query runs.

## 5.1 Setup

We run all experiments with Qwen3 4B (FP8) on one H100, and let each map write up to 1,024 output tokens. We use three queries from [QUAIL-B](https://github.com/fsdatalab/quail-bench), our benchmark of SQL queries with AI functions. In all three, each `AI.MAP` is a projection, not an aggregation: it writes one new column with one output per row, as in `SELECT c.id, AI.MAP(c.text, 'List the parties to this contract and the role of each.') AS parties FROM contracts c`. The queries are:

- **CUAD-21** runs 3 maps on each of 224 legal contracts, which are about 7,200 tokens each: list every obligation and who it binds, rewrite the key terms in plain English, and list every defined term with its definition.
- **CUAD-22** runs 16 maps on the same contracts. Each map covers one part of the contract, e.g., listing the parties, quoting the termination clauses, or summarizing each section in one sentence. Comparing CUAD-22 with CUAD-21 shows what happens when each document has many more maps.
- **AGENT-6** runs 3 maps on 1,772 snapshots of agent traces, which are about 9,700 tokens each: list the commands the agent ran, describe the agent's plan and how it changed, and list the files the agent edited.

For each query, we report throughput (input and output tokens per second) and KV regret (the tokens computed beyond the fewest the query needs).

We compare Quail, as described in [Section 4](#4-query-aware-scheduling-and-attention), with two vLLM baselines:

- **Stock vLLM.** We compile each query into LLM calls: one call for every map on every document. Then we pass all of the calls to `LLM.generate` in one batch, in random order.
- **vLLM-sorted.** Same as stock vLLM, but we sort the calls so that all of the calls on one document are next to each other. This way, vLLM's prefix caching can reuse each document's KV, which reduces KV regret.

## 5.2 How Fast Is AI.MAP?

**Quail's throughput is 2.0–6.2x that of stock vLLM!** ([Figure 3](#figure-3)) The biggest gain is on CUAD-22, where each contract has 16 maps.

Quail achieves 50–66% of the throughput of our speed-of-light estimates, which follow the roofline models described in our post on costing AI-powered filters<sup><a href="#note-8">8</a></sup> and assume unlimited KV memory.

## 5.3 Do We Need Adaptive Admission?

Recall that Quail decides how much KV to reserve for each request using [adaptive admission](#41-scheduling-which-requests-should-we-admit-into-a-batch). Do we really need this machinery, or could we get away with only the [shared-prefix attention](#42-forward-pass-reading-each-documents-kv-once)? To find out, we compare Quail with a version that uses the same attention but static admission: it reserves KV only for each request's prompt, as vLLM does.

With static admission, Quail evicts 103–884 requests per query. With adaptive admission, it evicts none on any of the three queries ([Figure 5](#figure-5)). On CUAD-22, this makes the query 1.09x faster. On CUAD-21 and AGENT-6, the effect is smaller: 0.97x and 1.04x, respectively.

<figure id="figure-5" style="width: min(40rem, calc(100vw - 3rem));">
<img src="{{ '/assets/blog/ai-map/headroom-ablation.svg' | relative_url }}" alt="Requests evicted on CUAD-21, CUAD-22, and AGENT-6 by Quail with static admission and by Quail with adaptive admission. Static admission evicts 103, 884, and 447 requests; adaptive admission evicts none.">
<figcaption>Figure 5. Requests evicted by Quail with static and adaptive admission. Both runs use the same attention.</figcaption>
</figure>

How accurate are Quail's estimates of output lengths? Quail reserves 1.3–1.9x the headroom its requests actually use: a lot more than needed! Each survival curve depends only on the map and the document's length, not its contents, so documents of similar length get the same headroom whether their outputs are short or long. Improving these estimates could let Quail run more requests at once and increase throughput.

## 5.4 What Does the Scheduler Learn?

So we're sold on adaptive admission. But what does it actually learn? Quail learns one survival curve for each map and each bucket of similar prompt lengths. [Figure 6](#figure-6) shows, for each map, the curve for the most common bucket in each query, at the end of the run.

<figure id="figure-6" style="width: min(52rem, calc(100vw - 3rem));">
<img src="{{ '/assets/blog/ai-map/survival-curves.svg' | relative_url }}" alt="Learned survival curves for each map, for the most common document length in each query. On CUAD-22, licensing finishes first and sections runs longest. On CUAD-21, the three maps end at similar lengths. On AGENT-6, edits and plan finish earlier than commands.">
<figcaption>Figure 6. Learned survival curves: the share of outputs still being written after each number of output tokens, for each map, for the most common document length in each query. On CUAD-22, only the shortest and longest of the 16 maps are labeled.</figcaption>
</figure>

First, output lengths vary a lot from map to map, even on documents of the same length. On CUAD-21, 77% of "definitions" outputs end within 800 tokens, while 12% of "plain terms" outputs are still being written at the 1,024-token limit. On CUAD-22, the 16 maps spread across the whole range: 60% of "licensing" outputs end within 400 tokens, while 19% of "sections" outputs hit the limit.

Second, the longer the prompt, the more headroom Quail reserves ([Figure 7](#figure-7)). As described in [Section 4.1](#41-scheduling-which-requests-should-we-admit-into-a-batch), if a request is evicted, its prompt has to be computed again, which costs more for a longer prompt.

We find that Quail reserves nothing extra for prompts under 512 tokens and room for at most 92 output tokens for prompts under 2,048 tokens, but room for 839–1,006 output tokens, nearly the whole 1,024-token limit, for prompts of 8,192 tokens or more.

<img src="{{ '/assets/blog/ai-map/admission-headroom.svg' | relative_url }}" alt="Output tokens reserved per request at admission, against prompt length, for each query. All three lines are at zero below 512 prompt tokens and at most 92 tokens below 2,048, then rise to 839 to 1,006 tokens for prompts of 8,192 tokens or more. A dashed line at zero marks vLLM, which reserves none.">
<figcaption>Figure 7. Headroom reserved per request at admission, in output tokens, against prompt length. vLLM reserves none (dashed line).</figcaption>
</figure>

<img src="{{ '/assets/blog/ai-map/headroom-over-run.svg' | relative_url }}" alt="Two panels for CUAD-22, at each scheduler step. Top: headroom reserved but not yet used, about 12,900 pages at the start, falling to about 4,300 by step 700, then between 3,100 and 8,300 pages for the rest of the run. <figcaption>Figure 8. Headroom reserved but not yet used (top), and requests decoding at once (bottom), at each scheduler step while Quail runs CUAD-22. Green ticks mark the steps where Quail admitted new requests.</figcaption>

The top panel shows the headroom: the KV pages Quail has reserved for outputs but not yet filled. It rises when Quail admits new requests, and falls as those requests generate output tokens. The bottom panel shows how many requests are decoding. Quail starts about 250 requests and reserves about 12,900 pages of headroom for them. Their headroom shrinks steadily as they generate output tokens. Quail admits new requests as earlier ones finish (the green ticks). For the rest of the run, a median of 198 requests decode at once, and Quail holds a median of about 6,400 pages of headroom.

Overall, Quail processes 2.0–6.2x more tokens per second than stock vLLM on our map queries. Interestingly, while adaptive admission removes every eviction, it improves query time by only up to 1.1x over static admission on these queries. Unlike in traditional databases, where page evictions can trigger expensive disk reads,<sup><a href="#note-9">9</a></sup> the cost of recomputing evicted KV is relatively small compared to the cost of executing the entire query. In other words, avoiding KV recomputation is less valuable than, simply, improving GPU utilization across the query.



# 6. Conclusion

In this post, we looked at how to make bulk text generation faster with `AI.MAP`. Unlike filters and classifiers, which typically generate only a few tokens, maps can generate any number of tokens per row. As the query runs, Quail learns how long each map's outputs tend to be and uses this to decide how much KV memory to reserve. And when multiple maps read the same document, Quail avoids redundant memory reads by sharing the document's KV during attention. Together, these optimizations let Quail process 2.0–6.2x more tokens per second than stock vLLM on our queries.

With `AI.MAP`, Quail now supports four kinds of AI functions in SQL: [filters and joins]({{ '/blog/introducing-quail/' | relative_url }}) with `AI.IF`, [classification]({{ '/blog/ai-classification/' | relative_url }}) with `AI.CLASSIFY`, [extraction]({{ '/blog/ai-extract/' | relative_url }}) with `AI.EXTRACT`, and now generation with `AI.MAP`. Try out [Quail](https://github.com/fsdatalab/quail), and if you like what we're building, give it a star on GitHub!
