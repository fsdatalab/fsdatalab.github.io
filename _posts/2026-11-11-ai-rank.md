<aside class="tldr"><strong>TL;DR:</strong> We were considering implementing a semantic top-k operator in Quail. Surprisingly, simply asking an LLM to score each record and sorting the scores was both faster and more accurate than pairwise comparison with the same LLM.</aside>

## 1. Introduction

A useful AI function in data processing is *semantic top-k*: given a question and a collection of records, return top k records that best match this question. For example, a sales team might ask, “Which calls most clearly show a customer's commitment to purchase?” A lawyer might want to find passages that best support a legal argument.

There are multiple approaches to find the top k items in a dataset according to some criteria, but which approach works best for typical, business-relevant data processing tasks? Common approaches use embedding-based retrieval or pairwise LLM comparisons. Surprisingly, a small extension of `AI.IF` to return a score—which we call `AI.SCORE`—was enough. Sorting the scores was more accurate and **8.2x faster per task** (geometric mean) than pairwise comparison on our three tasks.

In this blog post, we discuss how we explored different approaches to implement semantic top-k task in [Quail](https://github.com/fsdatalab/quail), our open-source SQL engine that supports AI functions.

We'll go through:

- Pointwise scoring
- Pairwise comparison
- Our experimental results
- Why pairwise comparison performs worse

## 2. Embedding-based Retrieval

One established approach is embedding-based retrieval. It computes the embeddings of questions and records separately, then ranks by cosine similarity between them. However, the LOTUS paper (Patel et al. 2025)[^1] pointed out that embedding-based retrieval performed well on relevance-based ranking but poorly on reasoning-based ranking. When similarity does not align with the natural language criteria, the accuracy of embedding-based retrieval can drop. Instead, we can use LLMs to evaluate records directly against the natural language ranking criteria.

A *reranker* runs a model with both the question and a record in the prompt to produce a number indicating how well they match, then sorts by that number. Each prompt is longer than embedding either input alone, and the model must run for every question-record pair instead of reusing stored record embeddings.

## 3. Pairwise Comparison

<aside class="review-note" style="margin: 1.25rem 0; padding: 0.85rem 1rem; border-radius: 6px; background: #edf3fc; color: #183b68; font-size: 0.9rem; line-height: 1.6;" aria-label="Comment from Shreya"><strong style="color: inherit;">Shreya:</strong> Can we include a clearer explanation of how LOTUS uses Quickselect to find the top k, perhaps with a small example?</aside>

Another approach to implement semantic top-k is using pairwise LLM comparisons and a quick-select top-k algorithm, the approach used in the LOTUS paper. More specifically, the algorithm selects a pivot record, compares it with other records, and repeatedly removes records that cannot be in the top k.

We wanted to use pairwise comparison for Quail's semantic top-k since it is conventionally considered better at accuracy. LOTUS[^1] reported that its pairwise-based top-k outperformed scoring each record independently on SciFact[^scifact] (0.765 vs. 0.457 nDCG@10) and HellaSwag-bench[^hellaswag] (0.919 vs. 0.091). Qin et al.[^2] also found that pairwise comparison outperforms scoring each record independently by more than 10% on average nDCG@10.

## 4. Pointwise Scoring

*Pointwise scoring* evaluates each record independently, then sorts the records by score and returns the top k. We implemented `AI.SCORE` as a small extension of `AI.IF`: both evaluate a yes/no question about a record, but `AI.SCORE` returns a number from 0 to 1 instead of a true/false answer.

For the Qwen3-4B model used here, Quail reads the model's logits for TRUE and FALSE at the answer position. A *logit* is the model's unnormalized value for a possible next token. Writing the TRUE and FALSE logits as t and f, Quail returns σ(t − f), where σ is the sigmoid function, which normalizes the score to between 0 and 1. A higher score means the model favors TRUE more strongly. The model is not trained to produce calibrated probabilities.

Here's an example query:

```sql
SELECT c.id,
       AI.SCORE(PROMPT(
         'Does the customer commit to buying, such as accepting the terms,
          agreeing to sign, or asking for the contract or paperwork?
          Interest, questions, or another meeting do not count.
          {0}
          Answer TRUE or FALSE.', c.transcript
       )) AS commit_score
FROM sales_calls c
WHERE c.deal_stage = 'Negotiation'
ORDER BY commit_score DESC, c.id
LIMIT 25
```

`AI.SCORE` with `ORDER BY` and `LIMIT` implements semantic top-k: score the records, sort by score, and return the best k.

## 5. Pointwise Beats Pairwise

We compared four methods on three business-relevant semantic top-k tasks:

- Sales: ranking sales calls by how close customers are to committing to a purchase
- Contract: ranking contracts by how clearly they restrict competition or require exclusive dealing
- Drug Safety: ranking biomedical articles by how clearly they document drug side effects, such as nausea or vomiting

All four methods use models with 4 billion parameters. **Pointwise** and **Pairwise** use Qwen3-4B for independent scoring and pairwise comparison, respectively. **Reranker** uses Qwen3-Reranker-4B to score each record independently, and **Retrieval** uses Qwen3-Embedding-4B for embedding-based retrieval.

**To our surprise, pointwise scoring achieves higher accuracy than pairwise comparison on all three tasks, while running 8.2x faster per task (geometric mean).**

In these experiments, more LLM calls did not buy higher accuracy. We are not the only ones to observe this: in another study of semantic top-k, Lenzi et al.[^3] compared two ranking strategies and found that the one requiring more LLM calls generally incurred higher costs without consistently achieving better accuracy.

One possible explanation is prior knowledge from training: a model trained on many sales call transcripts may already recognize signs of a customer's commitment to buying. The model may be able to judge a call on its own, without seeing other transcripts for comparison.

## 6. Why?

We dig into some possible reasons why pairwise comparison did not outperform pointwise scoring.

### 6.1 Comparison Can Be Inconsistent

We observed the following two types of inconsistent comparisons during experiments.

**The order of the two records in the prompt changes the answer.** Swapping the order of two records in the prompt can change which record the model prefers. We tested eight models of different sizes and types: Qwen3 models from 0.6B to 27B (plus Qwen3.6-35B-A3B, a mixture-of-experts model), LFM2-2.6B, two decision models (d1-2B and Decision-2.0-Kai-0.6B), and the Jev API.

Figure 2 shows, for each model, the fraction of pairs where the model picked the same record in both orders. Ideally, the fraction is 100%. Larger models were not consistently better: on Sales, Qwen3.8-27B picked the same record in both orders for only 14% of pairs, compared with 63% for Qwen3-4B. Specialized decision models such as Jev and d1-2B were more consistent on Sales, but still exhibited position bias: they picked the same record in only 70% and 73% of pairs, respectively.[^6]

**The model may need more reasoning before making a decision.** Some pairwise comparisons may require reasoning. To reduce latency, Quail scores the first token of the answer without generating the full response. We found that when allowed to generate the full response, Qwen3-4B's first-token decision differed from the final decision 28.89% of times on Sales (SF=0.1).

### 6.2 How Can Inconsistent Comparison Affect Top-k Results?

**One wrong comparison can eliminate a top-k record.** Quickselect repeatedly chooses a pivot record and uses comparisons with the pivot to decide which records to remove from consideration. If the LLM mistakenly places a true top-k record in the group being removed, the algorithm excludes it from the result. Later comparisons cannot recover the record. By contrast, `AI.SCORE` assigns each record one score. While the scores can be wrong, sorting them at least gives a consistent order.

**Pairwise comparisons lose the fine-grained information that scores give.** Pointwise gives score, while pairwise only gives win/loss, discarding how strong the model favors one choice over the other.[^4] As a result, an uncertain comparison can have the same impact as a confident one.

## 7. Conclusion

All in all, we decided against adding a dedicated semantic top-k operator: pairwise comparison was much slower and did not improve accuracy on our tasks. Scoring each record with `AI.SCORE` and sorting the scores worked better.[^5] If you have a use case that needs pairwise comparison, reach out to us—we'd like to hear about it.

As models improve, we are curious whether fine-tuning on domain-specific data could widen the advantage of scoring each record independently. Could we improve ranking using per-record labels, without collecting pairwise preferences? In the future, we also plan to explore reasoning-enabled AI operators and how to execute them efficiently.
